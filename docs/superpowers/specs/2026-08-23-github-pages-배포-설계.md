# GitHub Actions + Pages 배포 설계

> **작성일** 2026-08-23 · **BD 승인** 2026-08-23 (5개 결정 전부 O)
> **대상** ARENA LIVE 정적 사이트 → `https://barosportstv.com`
> 이 문서는 「무엇을 왜 그렇게 만들었는가」입니다. 실행 순서는 구현 계획서에 있습니다.

---

## 1. 목적

정적 사이트라 `assets/data.js` 에 넣은 TheSportsDB 키는 **브라우저 소스에 그대로 보입니다.**
남이 복사해 쓰면 우리 분당 100건 한도를 그 사람이 씁니다. 이걸 막는 것이 이 작업의 목적입니다.

부수적으로 얻는 것이 하나 더 있습니다. 브라우저가 API 를 직접 부르지 않게 되므로
**429 가 원천적으로 사라집니다** — 호출 횟수가 방문자 수와 무관해지고 크론 횟수만 남습니다.

## 3. 아키텍처

```
GitHub Actions (10분 크론)
  │  Secret: SPORTSDB_KEY
  ├─ npm run build:css        → assets/tailwind.css
  ├─ node tools/prebake.mjs   → data/**.json   (여기서만 API 를 부른다)
  ├─ 키 노출 검사              → 산출물에 키 문자열이 있으면 배포 중단
  └─ Pages 배포
                                    ↓
브라우저 ── data/**.json 만 읽는다 (API 키 없음 · 외부 호출 없음)
```

사이트는 **여전히 100% 정적**입니다. 서버가 늘어나지 않습니다.

## 4. 데이터 경로 단일화 — 「한 줄 변경」의 구조적 근거

### 4.1 지금의 문제

네트워크 진입점이 두 군데로 갈라져 있습니다.

| 위치 | 코드 |
|---|---|
| `assets/data.js:182` | `fetch(BASE + 'eventsday.php?d=' + utcKey + '&s=' + …)` |
| `assets/data.js:194` | `function getJson(path) { return fetch(BASE + path) … }` |

두 곳이라 출처를 바꿀 때 두 곳을 고쳐야 하고, 빠뜨리면 한쪽만 프리베이크를 읽습니다.

### 4.2 설계

`fetchUtcDay` 도 `getJson` 을 쓰게 고쳐 **진입점을 하나로 만듭니다.** 그 위에 출처 설정을 둡니다.

```js
/* 데이터 출처. 여기 두 줄만 바꾸면 프리베이크 ↔ 실시간 프록시가 갈린다.
   호출하는 쪽(data-pages.js 5곳)은 한 글자도 바꿀 필요가 없다. */
var SOURCE = {
  mode: 'prebake',        // 'prebake' | 'live'
  base: './data/'         // live 로 바꾸면 프록시 주소
};
```

`getJson(path)` 이 `mode` 를 보고 갈라집니다.

| `mode` | `getJson('eventsday.php?d=2026-08-23&s=Soccer')` 이 읽는 곳 |
|---|---|
| `prebake` | `./data/eventsday/2026-08-23_Soccer.json` |
| `live` | `<base>eventsday.php?d=2026-08-23&s=Soccer` (경로를 그대로 붙인다) |

### 4.3 엔드포인트 → 파일 이름 매핑

프리베이크 스크립트와 브라우저가 **같은 규칙**을 써야 합니다. 규칙은 한 곳에만 적고
양쪽이 그 규칙을 공유합니다 (`tools/prebake.mjs` 는 `assets/data.js` 를 읽을 수 없으므로
규칙을 두 번 적게 됩니다 — **그래서 규칙을 이 표로 고정하고, 양쪽에 이 표를 주석으로 남깁니다**).

| 호출 | 파일 |
|---|---|
| `eventsday.php?d=<날짜>&s=<종목>` | `data/eventsday/<날짜>_<종목에서 공백을 _ 로>.json` |
| `searchteams.php?t=<팀명>` | `data/teams/<팀명>.json` (`Manchester City` → `manchester_city.json`) |
| `eventsnext.php?id=<팀id>` | `data/eventsnext/<팀id>.json` |
| `lookuptable.php?l=<리그id>&s=<시즌>` | `data/table/<리그id>_<시즌>.json` |
| `lookupevent.php?id=<경기id>` | `data/events/<경기id>.json` |

파일 이름은 **소문자·영숫자·`_`·`-`·`.` 만** 남기고 나머지는 `_` 로 바꿉니다
(팀명에 한글·점·슬래시가 섞여 와도 안전한 파일 이름이 되게).

### 4.4 파일이 없으면 어떻게 되는가

404 → `getJson` 이 기존대로 `null` 을 돌려줍니다 → **하드코딩 화면이 그대로 남습니다.**

이건 새 규칙이 아니라 `assets/data.js` 첫 주석에 적힌 **점진적 향상 원칙이 그대로 작동하는 것**입니다.
프리베이크가 일부 실패하거나 상한에 걸려 빠진 팀이 있어도 화면이 비지 않습니다.

## 5. 프리베이크 스크립트 `tools/prebake.mjs`

Node 20 내장 `fetch` 만 씁니다. **새 의존성 0.** 키는 `process.env.SPORTSDB_KEY` 에서만 읽고,
없으면 즉시 실패합니다 (조용히 무료 키로 떨어지지 않게).

### 5.1 순서

1. `eventsday` **12건** — 종목 4개(`Soccer`·`Basketball`·`Baseball`·`American Football`) × UTC 3일(`-1`,`0`,`+1`)
   - UTC 3일인 이유: 한국(UTC+9) 기준 하루가 UTC 이틀에 걸치므로. `assets/data.js` 의 `eventsForLocalDay` 와 같은 범위
2. 응답에서 **팀명**(`strHomeTeam`·`strAwayTeam`)과 **경기 id**(`idEvent`)를 모은다
3. 구울 팀 목록을 정한다
   - `assets/teams.js` 사전 **21팀은 항상** (검색·팔로우·홈에서 갈 수 있는 팀은 전부 여기다)
   - 2단계에서 나온 팀을 **최대 60팀까지** 추가 (경기 시각이 이른 순)
4. 팀마다 `searchteams` → 응답의 `idTeam`·`idLeague` 로 `eventsnext`
5. 리그마다 `lookuptable` (시즌 추정값은 `assets/data-pages.js:334` 의 기존 로직과 같게)
6. `data/events/<경기id>.json` 을 **API 를 부르지 않고** 만든다 — 추가 호출 0건
   - `data-pages.js:172` 는 `?event=<id>` 가 **오늘 목록에 없을 때만** `lookupevent` 를 부른다
   - UTC 3일치를 받았으므로 어제·내일 경기는 「오늘 목록」에 없어서 이 경로를 탄다
   - 그런데 그 경기의 전체 정보는 **1단계 `eventsday` 응답에 이미 들어 있다.**
     그래서 받아둔 이벤트를 id 별로 쪼개 파일로 쓰기만 하면 된다
   - 3일 창을 벗어난 지난 경기의 `?event=` 링크는 구울 수 없다(id 공간이 무한).
     그 경우 하드코딩 화면이 남는다 — 4.4절
7. `data/manifest.json` 을 쓴다

### 5.2 호출 한도 준수

유료 Single Developer 는 **분당 100건**입니다. 호출 제한기를 넣어 **분당 90건**을 넘지 않게 합니다
(10% 여유). 예상 총량:

| 항목 | 건수 |
|---|---|
| `eventsday` | 12 |
| `searchteams` (21 + 최대 60) | ≤ 81 |
| `eventsnext` | ≤ 81 |
| `lookuptable` | ≤ 20 |
| `lookupevent` | **0** (5.1의 6단계 — 받아둔 응답을 쪼개 쓴다) |
| **합계** | **≤ 194** |

분당 90건이면 **약 2분 10초**. 10분 주기에 여유 있게 들어갑니다.

### 5.3 조용히 버리지 않는다

60팀 상한에 걸려 못 구운 팀은 **이름을 전부** `data/manifest.json` 과 워크플로 로그에 남깁니다.
"다 구웠다"로 읽히면 안 됩니다.

```json
{
  "generatedAt": "2026-08-23T06:00:00Z",
  "counts": { "eventsday": 12, "teams": 81, "eventsnext": 81, "table": 18 },
  "skippedTeams": ["…"],
  "failed": ["…"]
}
```

### 5.4 부분 실패

호출 하나가 실패하면 그 파일만 안 만들고 **스크립트는 계속 진행합니다.**
그 화면은 하드코딩으로 남습니다(4.4절). `eventsday` 12건이 **전부** 실패한 경우에만
배포를 중단합니다 — 그건 키가 죽었다는 뜻이므로 빈 사이트를 올리면 안 됩니다.

## 6. canonical 을 `/schedule.html` 로 바로잡는다

현재 6장의 canonical 이 **확장자 없는 주소**입니다(`index.html:9` 외 5곳).

```html
<link rel="canonical" href="https://example.com/schedule">
```

GitHub Pages 는 파일 그대로 `/schedule.html` 을 내보냅니다. 그대로 올리면
**canonical 이 404 를 가리킵니다** — 실제 SEO 결함입니다.

두 가지 길이 있고 **확장자를 붙이는 쪽을 택했습니다.**

| 방법 | 고칠 곳 | 위험 |
|---|---|---|
| 파일을 `schedule/index.html` 로 옮긴다 | 6장 이동 + 내부 링크·JS 가 참조하는 `*.html` **전부** | 방금 안정화한 반응형·덮개 링크 화면을 다시 건드린다 |
| **canonical 을 `/schedule.html` 로 맞춘다** | **canonical 6곳만** | 없음 |

목적은 「404 를 가리키는 canonical 을 없애는 것」입니다. 주소 미관을 위해
안정된 화면을 흔들 이유가 없습니다.

## 7. 도메인 연결

- 저장소 루트에 `CNAME` 파일 (`barosportstv.com` 한 줄)
- `example.com` → `barosportstv.com` **18곳** 치환 (6장 × canonical·og:image·JSON-LD `url`)
- DNS 설정값은 별도 안내서로 남깁니다. **BD 가 도메인 등록기관에서 직접 넣어야 합니다** — AI 가 대신 할 수 없습니다

## 7.1 배포 산출물에 넣지 않는 것

저장소에는 `_백업_수정전/`(수정 전 백업)과 `_검토_스크린샷/`(검토용 스크린샷)이 있습니다.
그대로 올리면 **`barosportstv.com/_검토_스크린샷/…` 로 누구나 볼 수 있게 됩니다.**

지우지 않습니다(BD 자산입니다). 대신 배포할 것만 골라 담습니다.

| 담는다 | 담지 않는다 |
|---|---|
| `*.html` 6장 · `CNAME` · `assets/` · `data/` | `_백업_수정전/` · `_검토_스크린샷/` · `docs/` · `tools/` · `tests/` · `src/` · `node_modules/` · `package*.json` · `assets/img/출처.md` |

## 8. 키 노출 방지 장치

배포 직전 단계에서 산출물 전체에 키 문자열이 있는지 검색하고, **하나라도 나오면 배포를 중단**합니다.
사람의 주의력에 기대지 않고 구조로 막습니다.

## 9. 크론이 60일 뒤 멈추는 함정

GitHub 은 **저장소에 커밋이 60일간 없으면 스케줄 워크플로를 자동으로 끕니다.**
크론이 도는 것 자체는 활동으로 세지 않습니다. 사이트를 한동안 손대지 않으면 조용히 멈춥니다.

방지책: 주 1회 `data/manifest.json` 을 `main` 에 커밋하는 짧은 잡을 함께 둡니다.

## 11. 나중에 바꿀 수 있는 것 (기록용 — BD 요청 2026-08-23)

### 11.1 진짜 실시간이 필요해지면 → Cloudflare Workers 프록시

**10분 주기로는 「실시간 중계」라는 이름에 못 미칩니다.** 경과 시간 시계는 `app.js` 가
브라우저에서 올리므로 화면은 살아 있어 보이지만, **득점은 최소 10분 늦게 뜹니다.**

전환 방법:

1. Cloudflare Workers 에 프록시를 만든다 — 키를 Worker 환경변수에 두고 TheSportsDB 로 중계
2. `assets/data.js` 의 `SOURCE` 를 바꾼다

```js
var SOURCE = { mode: 'live', base: 'https://api.barosportstv.com/' };
```

**이 두 줄이 전부입니다.** 4.2절의 단일 진입점 설계가 이걸 보장합니다.
호출하는 쪽(`data-pages.js` 5곳)과 프리베이크 산출물 규칙은 건드리지 않습니다.
프리베이크 파이프라인은 그대로 둬도 되고(프록시 장애 시 대비), 지워도 됩니다.

바꿔도 이번 작업이 낭비되지 않는 이유: 이번에 만드는 것의 핵심은 **키를 브라우저에서
빼내는 것**이고, 그건 두 방식이 공유하는 목표입니다.

### 11.2 유료 키를 받으면 → 리그를 골라 부른다

지금은 종목 단위로 부릅니다(`eventsday.php?s=Soccer`). 무료 키가 리그를 고를 수 없어서입니다.
그래서 하위 리그(USL·아르헨티나 2부)가 섞여 옵니다.

유료 키를 받으면 **우리가 보여줄 리그만** 부르도록 바꿉니다. 그러면

- 등장 팀 수가 줄어 **60팀 상한에 닿지 않습니다** (4번 결정의 「잃는 것」이 사라집니다)
- 한글 팀명 비율이 올라갑니다 (사전 21팀이 실제로 화면에 나타납니다)
- 팀 검색 정확도가 올라갑니다 (지금은 `Tottenham` 이 여성팀으로 잡힙니다)

**어느 리그를 보여줄지는 BD 결정 사항입니다.** 지금 정하지 않습니다.

### 11.3 갱신 주기

`.github/workflows/deploy.yml` 의 `cron` 한 줄입니다. 5분이 최소값이고, 그 이하는 불가능합니다.
